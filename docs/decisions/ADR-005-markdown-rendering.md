# ADR-005: Server-side Sanitized Markdown Rendering

**Status:** Accepted
**Date:** 2026-10-12
**Owner:** planner
**Supersedes:** —

## Context

Amalthea stores analyst-authored rich text in two places that the UI renders:

- **Case `description`** (`Case.description`, documented as Markdown in AGENTS.md §3).
- **Comment / ledger bodies** (the collaborative live ledger, AGENTS.md §2 Module B).

Plan `PLAN-2026-10-11-ui-completeness.md` item **D3** requires these to render as
**sanitized CommonMark**, server-side, with a strict allow-list. Two platform constraints apply:

- **CSP (ADR-003):** `script-src 'self'` / `style-src 'self'`, **no inline scripts or styles**.
  Rendering must not introduce inline assets, and the UI must degrade without JS (HTMX is
  progressive enhancement only).
- **XSS (AGENTS.md §5/§6, plan §9):** the ledger is attacker-adjacent content (analysts paste
  text from phishing emails, tickets and CTI reports). Any HTML executed from a ledger body is
  a stored-XSS vector against every analyst in the org.

The repository is public and its runtime closure is pinned **with hashes** (`requirements/base.txt`,
regenerated by `scripts/lock.sh`). At decision time the closure contained **no** Markdown parser and
**no** HTML sanitizer; `markdown-it-py`/`mdurl` were present only in the *dev* closure (transitive via
`rich`), and `nh3` was absent entirely.

This ADR records Open Question **Q1** of the UI-completeness plan (decided 2026-10-12, Option A).

## Decision

**Render analyst Markdown to HTML server-side with `markdown-it-py` (CommonMark) and sanitize the
result with `nh3` (Ammonia bindings) behind a strict allow-list, exposed as one template filter.**

1. **Parser — `markdown-it-py`, CommonMark.** `MarkdownIt("commonmark", {"html": False})`: raw HTML
   in the source is **not** passed through (it is escaped as text). No extensions, no plugins.
2. **Sanitizer — `nh3`, applied unconditionally as defence-in-depth.** Even with `html=False`, the
   rendered fragment is re-parsed and filtered by `nh3.clean()` against an explicit allow-list.
   Raw HTML, `<script>`, `<style>`, `<iframe>`, `<object>`, `<form>` and event-handler attributes are
   dropped. URL attributes are restricted to `http`, `https`, `mailto` and relative links; `javascript:`
   and `data:` are denied. `nh3` is the **single trusted XSS boundary** — the filter never emits
   un-sanitized parser output.
3. **Server-side, in the template layer.** One filter (`ui_tags.markdown`) is the only render path;
   templates use `{{ value|markdown }}` instead of `{{ value }}` for the two fields above. No rich text
   is rendered client-side, preserving the CSP and the no-JS fallback.
4. **Plain-text fallback preserved.** Empty input renders nothing (not an empty `<p>`); non-Markdown
   text renders as escaped text. Failure is fail-closed: if rendering or sanitizing raises, the filter
   returns the input **escaped** (never raw).
5. **Pinned, hash-verified dependencies.** `markdown-it-py==4.2.0`, `mdurl==0.1.2` (promoted from the dev
   closure to runtime) and `nh3==0.3.7` are added to `requirements/base.txt`. `scripts/lock.sh` gains a
   small, **declared** `BASE_ALLOW` allow-list authorising exactly these three additions; any *other*
   closure drift still aborts the lock pass.

## Alternatives Considered

| Option | Pros | Cons |
|--------|------|------|
| **A. `markdown-it-py` + `nh3`** (chosen) | Active, spec-compliant CommonMark; Rust sanitizer (Ammonia) is memory-safe and purpose-built; `nh3` is maintained; explicit allow-list API | Two new runtime deps (+`mdurl`); sanitizer is a security-critical dependency that must be kept current |
| B. `bleach` | Well-known API | **Deprecated/unmaintained** upstream (archived); pulls `html5lib`; not advisable for a security boundary |
| C. Hand-rolled subset (regex/`markdown` lib only) | No new deps | Home-grown sanitizers are a classic XSS source; larger review burden than the dependency it avoids; plan explicitly did not recommend it |
| D. Client-side rendering (e.g. marked.js) | — | Violates CSP/no-inline and the no-JS fallback; moves the XSS boundary into the browser; rejected outright |
| E. Render raw HTML, rely on CSS/`target` | trivial | Stored XSS by design; rejected |

**`markdown-it-py` alone is insufficient** (it can pass raw HTML when configured to, and does not
sanitize URLs); the sanitizer is the actual security control.

## Consequences

- **Runtime closure grows** by 3 packages (`markdown-it-py`, `mdurl`, `nh3`); `mdurl`/`markdown-it-py`
  move out of the dev closure into base (dev keeps them transitively via `-r base.txt`).
- **`scripts/lock.sh` now carries a declared `BASE_ALLOW` allow-list.** This is the sanctioned way to
  add a runtime dependency: the entry documents the deliberate, reviewed addition, while the pass still
  refuses *unexpected* drift and *version changes* of existing pins.
- **The sanitizer is load-bearing security.** An active monitoring expectation exists: `nh3` (and
  `markdown-it-py`) advisories must be tracked and the pins bumped promptly. If `nh3` is ever
  abandoned, D3 must be re-decided (this ADR revisited), not silently left on a stale boundary.
- **Rendering is pure and cheap but cached.** The filter is a pure function of its input string; a
  bounded `functools.lru_cache` avoids re-parsing list pages. Cache is per-process (not shared) — fine
  for rendering, must simply be bounded to avoid unbounded memory.
- **CSP unchanged.** `nh3`'s allow-list excludes inline-capable elements and event handlers, so no
  `'unsafe-inline'` is ever required, and `test_ui_inline_assets.py` stays green.
- **New test obligation:** `tests/conformance/test_ui_markdown.py` drives `<script>`, `<img onerror>`,
  `<iframe>`, `javascript:`/`data:` links, raw HTML and nested-emphasis payloads through the filter and
  asserts the dangerous constructs are absent from the output.

## Verification

- `make lock` regenerates deterministically (run twice → byte-identical) and the closure invariant
  holds (only the three declared additions).
- `make check` passes (ruff, mypy, migrations, tests, css compile).
- `tests/conformance/test_ui_markdown.py` — XSS payload suite is green.
- Manual: a case description containing `**bold**` and `[x](javascript:alert(1))` renders bold text and
  an inert link with no script execution.
